## 5. 검증과 제공물

- [ ] 서로 다른 브라우저 세션 A와 B를 사용한다. A에서 사진을 등록하면 B에, B에서 손그림을 등록하면 A에 카드가 새로고침 없이 나타나는지 확인한다.
- [ ] A와 B에서 같은 포스트잇을 연다. A가 댓글을 달면 B의 상세 댓글과 카드 댓글 수가 새로고침 없이 갱신되는지 확인한다. 상세를 닫은 보드에서도 댓글 수가 갱신되는지 확인한다.
- [ ] 운영자가 새 경로에 교체 이미지를 업로드한 뒤 `image_path`를 변경한다. 두 세션의 상세 이미지와 썸네일이 새로고침 없이 갱신되는지 확인한다.
- [ ] B의 연결을 끊은 동안 A가 댓글을 등록한다. B를 재연결했을 때 놓친 댓글과 댓글 수가 복구되고 같은 댓글이 중복 표시되지 않는지 확인한다.
- [ ] 모바일에서 첨부, 터치 그리기, 카드 열기를 확인한다. 등록 실패 시 입력이 유지되고 재시도로 저장할 수 있는지 확인한다.
- [ ] 실제 Supabase에 연결해 위 시나리오를 검증하고 빌드를 확인한다. 앱 소스, SQL 마이그레이션, `.env.example`, README를 제공한다. README에는 로컬 실행, Supabase 테이블·Storage 설정, 관리자 이미지 교체와 두 세션 검증 절차를 적는다.

## 6. 인증·인가 구현 및 마이그레이션

### 6.1 준비와 데이터 확장

- [ ] 공개 열람과 이메일 인증 회원의 등록을 기준으로 개발·스테이징·운영의 Auth Site URL, 콜백·재설정 리디렉션 허용 목록과 메일 발송을 구성한다. 운영 주소와 발신 도메인을 확정하고 테스트 계정으로 실제 메일 수신부터 확인한다. [Supabase 이메일·비밀번호 인증](https://supabase.com/docs/guides/auth/passwords)
- [ ] 적용된 마이그레이션과 현재 DB 역할별 권한·RLS, Realtime 발행 대상, Storage 버킷을 확인한다. DB의 복구 지점을 확보하고 `moa-artwork` 객체의 목록과 복사본을 별도로 보관한다. 기존 글·댓글 수, 이미지 경로와 참조 누락 여부를 검증 기준으로 기록한다. [Supabase 백업 범위](https://supabase.com/docs/guides/platform/backups)
- [x] 비공개 작성자 연결 테이블, 등록 RPC 두 개와 `moa-artwork` 쓰기 제한 정책을 추가한다. RPC 생성과 실행 권한 설정은 같은 트랜잭션에서 처리한다. 첫 마이그레이션은 기존 등록 함수와 호환되고, 후속 마이그레이션은 서버 역할의 직접 INSERT 권한을 회수한다.
- [ ] 전환 전 글·댓글은 작성자 미연결 상태로 보존한다. 닉네임만으로 확인할 수 있는 계정 정보가 없으므로 이관할 작성자 데이터가 없다. 기존 UUID, 댓글 관계, 작성 시각과 객체 경로를 보존한다. 스테이징에서 운영 유사 데이터와 빈 DB 양쪽에 마이그레이션을 적용해 조회 결과와 제약을 확인한다.

### 6.2 세션·등록 구현

- [x] 가입, 이메일 인증, 로그인·로그아웃, 비밀번호 재설정과 콜백을 구현한다. 작성 화면과 상세 창 안에서 로그인하도록 해 입력을 보존한다. 브라우저에서 세션을 저장·갱신하고 공개 키를 `apikey`에, 액세스 토큰을 `Authorization`에 보낸다.
- [x] `moa-write`에서 본문 파싱·업로드 전에 `auth.getUser(accessToken)`으로 이메일 인증을 마친 일반 계정인지 확인한다. 유효하지 않은 사용자 세션은 `401`, 작성 자격을 충족하지 못한 계정은 `403`, 일시적 Auth 장애는 `503`으로 처리한다. 자격 검증과 서버 쓰기에 별도 클라이언트를 사용한다. [Supabase 함수 인증](https://supabase.com/docs/guides/functions/auth) · [getUser](https://supabase.com/docs/reference/javascript/auth-getuser)
- [ ] 스테이징에서 `verify_jwt = true`와 실제 프로젝트 서명 키의 호환성을 확인한다.
- [x] 글·댓글의 UUID 충돌 판정을 등록 RPC에서 처리한다. 최초 요청은 원본 행과 작성자 연결을 함께 커밋하고, 같은 계정·요청 ID·입력 지문에는 같은 성공 응답을 반환한다. 다른 계정, 다른 입력 또는 작성자 미연결 행과의 충돌은 `409`로 처리한다. 계정이 바뀐 뒤 제출하면 새 요청 ID를 사용한다.
- [x] 이미지 검증을 유지한다. 업로드 뒤 DB 응답이 불명확하면 객체를 보존하고, 같은 요청이 재시도될 때 등록 RPC가 앞선 저장 결과를 판별한다. 미참조 이미지 정리는 운영 시 유예 기간 뒤 DB 참조와 진행 중인 요청 여부를 확인하고 수행한다.

### 6.3 운영 전환과 복구

1. 스테이징에서 아래 검증을 통과한 뒤 운영에 Auth 설정과 6.1의 추가 마이그레이션을 적용한다. 공개 페이지와 기존 함수의 호환성을 먼저 확인한다.
2. 전환 시 기존 `moa-write`를 같은 경로에서 인증 필수 버전으로 교체한다. 직전까지 수락된 요청이 끝난 뒤 후속 SQL로 서버 역할의 공개 테이블 직접 `INSERT`를 회수한다. 운영자의 이미지 교체에 필요한 권한과 등록 RPC 실행 권한을 확인한다. 이전 클라이언트의 anon 토큰 요청이 거부되고 새 함수는 로그인 계정의 등록만 수락하는지 확인한다.
3. 새 프런트엔드를 공개하고, 구버전 탭에서 쓰기가 거부되면 새로고침 후 로그인하도록 안내한다. 함수 교체와 새 화면 공개 사이에는 신규 등록이 일시 중단될 수 있으므로 이 구간을 공지한다. 새 글·댓글의 작성자 연결, 기존 이미지·댓글 조회, 인증 오류와 저장 오류 추이를 확인한다. README에 환경 설정, 전환 순서, 운영자 이미지 교체 절차를 반영한다.
4. 기존 이미지·댓글이 누락되거나 인증 우회 또는 지속적인 저장 실패가 확인되면 전환을 중단한다. 공개 읽기를 제공하면서 검증된 인증 필수 버전으로 복구하거나 쓰기를 일시 차단한다. 적용한 추가 테이블과 전환 뒤 등록된 데이터는 보존하고, 장애는 후속 마이그레이션으로 수정한다. DB 복원이 필요한 경우 복구 시점 이후 변경분과 Storage 객체를 함께 대조한다.

### 6.4 완료 기준

- [ ] 비로그인·미인증·정상 회원 계정 A·B와 운영자로 검증한다. 가입 및 실제 이메일 인증, 비밀번호 재설정, 새로고침, 로그아웃, 토큰 만료 후 재로그인과 작성 내용 보존을 확인한다.
- [ ] 호스팅 프로젝트의 기본 메일과 앱 템플릿에서 각각 가입 확인과 재설정 링크를 확인한다. 기본 Site URL로 돌아왔을 때의 이동, 만료 링크 안내, 가입 확인 메일 재발송을 확인한다.
- [ ] 브라우저 UI와 별개로 함수·REST·RPC·Storage를 직접 호출한다. 공개 키나 위조·만료 토큰으로 등록할 수 없고, 양쪽 공개 역할의 직접 쓰기와 작성자 정보 조회가 차단되는지 확인한다. 인증 회원의 정상 등록과 운영자의 이미지 교체를 확인한다.
- [ ] A의 동일 요청을 반복·동시 전송하고 B가 같은 ID로 제출한다. 글과 댓글은 각 1건만 저장되고, 충돌에서 작성자나 이미지가 바뀌지 않으며, 업로드 실패와 등록 응답 유실 후에도 데이터가 일관적인지 확인한다. 회원 삭제 시 공개 글·댓글과 이미지가 유지되고 작성자 연결의 계정 ID가 비워지는지 확인한다.
- [ ] 인증 전후의 두 브라우저에서 공개 조회, 사진·손그림, 댓글·댓글 수, 이미지 교체, 실시간 재접속, 세션 변경을 재검증한다. 전환 전후 기존 행의 ID·필드·댓글 관계·이미지 접근성을 대조하고, 공개 API와 Realtime payload에 계정 ID·이메일이 없는지 확인한다. `npm.cmd run typecheck`와 `npm.cmd run build`를 실행한다.
